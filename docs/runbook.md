# Ранбук v1 (устаревший)

Пошаговый порядок для root-агента. Роль root — планирование, привязка заданий, каноническая приёмка
и финальный русский отчёт; сам root не является исследовательской ролью.

## Предусловия

- `python3 scripts/preflight.py` → `passed: true`.
- Цель, охват и условие остановки есть в запросе пользователя или в `tasks/`.
- `config/founder-profile.yaml` не противоречит запросу; неизвестное остаётся неизвестным.

## Порядок действий

1. **Создать прогон** (цель, охват, условие остановки, лимиты, снапшот возможностей):
   ```
   python3 scripts/app.py create-run --run <run-id> --objective "<цель>" --scope mining \
     --stopping-condition "<условие>" --config <limits.json> --capabilities <capabilities.json> \
     --brief tasks/standing-objective.md
   ```
2. **Дешёвые гипотезы (только mining)**: до control plane накопить staging-файл, где нет claims и
   приёмки. Первый прогон идёт по `config/research-policy.yaml` → `funnel.first_run` (40 → 12 → 5 → 3),
   целевой масштаб — `funnel.target_scale` (300 → 60 → 15 → 5).
   ```
   python3 scripts/hypotheses.py add --run <run-id> --input <hypotheses.jsonl>
   python3 scripts/hypotheses.py audit --run <run-id>
   python3 scripts/hypotheses.py select --run <run-id> --limit 12
   ```
   Промотируются только отобранные гипотезы; остальные остаются в staging и не считаются кандидатами.
   Портфельные квоты считаются по принятому корпусу, а не по staging.
   `preferred_industry_buckets` задают сетку для дешёвого anti-bias staging, но не закрытый словарь:
   discovery сохраняет более точную отрасль из явно заданного run scope, а portfolio audit помечает
   её как находящуюся вне предпочтительной сетки.
3. **Проверить маршрутизацию моделей.** Роли получают провайдера и модель из
   `config/model-routing.yaml`; `null` означает выбор во время запуска. Значения попадают в
   замороженный packet задания (`execution_policy`), поэтому менять их нужно до `queue`:
   ```
   python3 scripts/routing.py show
   python3 scripts/routing.py set --role skeptic --provider deepseek --model deepseek-reasoner
   python3 scripts/routing.py validate
   ```
   Skeptic и Judge имеет смысл держать на другой модели, чем авторы проверяемых материалов:
   общая модель не даёт независимости, и это фиксируется в политике.
4. **Поставить discovery** по отрасли покупателя из `config/portfolio.yaml`:
   ```
   python3 scripts/app.py queue --run <run-id> --candidate <candidate-id> --role discovery --input <packet.json>
   ```
5. **Выполнить задание.** Штатный путь — собственный исполнитель: он сам привяжется к заданию с
   фактической моделью, соберёт источники и запишет результат.
   ```
   python3 scripts/worker.py --run <run-id> --assignment <candidate-id>-discovery
   ```
   Параллельно запускать не больше `max_active_agents`. Альтернатива — запустить агента
   инструментом делегирования с провайдером и моделью из packet и **привязать его фактический ID
   и модель вручную**:
   ```
   python3 scripts/app.py bind --run <run-id> --assignment <candidate-id>-discovery --agent-id <actual-id> \
     --provider <фактический провайдер> --model <фактическая модель>
   ```
   Запрошенная и фактическая модель хранятся отдельно: если runtime дал не то, что запрошено, это видно
   на дашборде, а не скрыто.
   Запись в очереди не является запуском агента. Пока нет `bind`, работа не выполнена.
   На один ход воркера выдаётся одно задание. В промпте явно запретите воркеру запускать
   `scripts/app.py`, менять manifest, принимать результаты, записывать решения, отменять других
   воркеров и финализировать run. Следующее задание выдавайте только после сверки результата текущего.
6. **Принять результат** после проверки схемы, хешей, авторства и ссылок на утверждения:
   ```
   python3 scripts/app.py accept --run <run-id> --assignment <assignment-id> --result <path>/result.json
   ```
7. **Light validation**: один экономичный discovery-worker собирает сигналы workflow, расходов и
   повторяемости. `status` рассчитывает Investigation Priority по принятым claims до Judge.
8. **Serious validation**: для отобранных кандидатов проверить нужные аспекты. Один допустимый worker
   может выполнить несколько facets, но результаты остаются отдельными и замороженными.
9. **Deep investigation**: `Skeptic` независимо проверяет полный frozen snapshot всех принятых claims,
   затем свежий независимый `Judge` оценивает тот же корпус. Discovery-автор не валидирует кандидата;
   Skeptic и Judge не переиспользуют контекст и не являются авторами проверяемых материалов.
10. **Отправка отчёта** (только если пользователь авторизовал отправку и заполнены
   `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`):
   ```
   python3 scripts/telegram.py check
   python3 scripts/telegram.py send --run <run-id> --file runs/<run-id>/report.md --caption "<тема>"
   ```
   Отправка не заменяет архив прогона: результат (включая отказ Telegram) сохраняется в `sources/`.
   Токен в артефакты и URL не попадает.
11. **Решение** и **отчёт**:
   ```
   python3 scripts/app.py decide --run <run-id> --candidate <cid> --status <qualified|rejected|deferred|duplicate> \
     --reason "<причина>" --author-id <actual-id> --claim-id <claim-id>
   python3 scripts/app.py report --run <run-id>          # машинная секция и предварительный PDF
   # narrative на русском root пишет вне machine-маркеров
   python3 scripts/app.py report --run <run-id>          # актуальный PDF из финального Markdown
   # root визуально просматривает каждую PNG-страницу в report-preview/
   python3 scripts/app.py pdf-review --run <run-id> --author-id <actual-id> --reason "<что проверено>"
   python3 scripts/app.py finalize --run <run-id>
   ```
   `report.pdf` — основной deliverable. `finalize` отклоняет устаревший PDF, отсутствие встроенного
   кириллического шрифта, потерянные русские слова, неполные previews или квитанцию от другого SHA.

   Перед финализацией проверьте `status.execution_health`. Значение `blocked` означает, что хотя бы
   одно уже поставленное задание закончилось `rejected` или `cancelled`; такой прогон нельзя завершить
   как успешный. Сначала восстановите задание. Технический отказ воркера отмечайте
   `cancel --failure-kind execution`: повтор после него не расходует лимит исследовательских попыток.
   `no_data` записывается только для технически успешного запроса без релевантных результатов.

   Основной отчёт отвечает на решение. Для shortlist укажите покупателя, триггер, оплачиваемую работу,
   границу продукта, формат поставки, единицу оплаты, предполагаемый inbound-канал, главный риск и
   самый дешёвый решающий тест. Подробности retries, worker IDs и хешей остаются в проверяемой сводке.

## Сбор данных

- `scripts/search.py` — машинный веб-поиск (Brave по умолчанию, Tavily как запасной). Ключи берутся из
  окружения или `.env.local`; `providers` показывает доступность без сети.
  ```
  python3 scripts/search.py providers
  python3 scripts/search.py search --run <run-id> --query "<запрос>" --count 10 --assignment <assignment-id> --role <role>
  python3 scripts/search.py fetch --run <run-id> --url <url> --assignment <assignment-id> --role <role>
  python3 scripts/search.py log --run <run-id>
  ```
  `--assignment` и `--role` записывают, кто именно тянул источник (`runs/<run-id>/source_usage.jsonl`
  и штамп в sidecar). Они не входят ни в `source_id`, ни в `logical_query_id`, поэтому не меняют ни
  архив, ни бюджет. Без них источник виден на дашборде как «не атрибутирован».
  Поведение при сбоях: нет ключа → `capability_unavailable`, стадия докладывается как заблокированная,
  скрапинг вместо поиска не подставляется. `429` или transport failure допускает одну смену провайдера.
  Пустая выдача → `[]` без расширения запроса. Один semantic query имеет общий `logical_query_id` и
  считается один раз; provider attempts и rate-limit/transport/HTTP/parse failures сохраняются отдельно.
  Запуски к одному провайдеру сериализуются между worker-процессами. Для Brave по умолчанию
  выдерживается интервал 1.05 секунды; если резервного провайдера нет, после `429` Brave повторяется
  один раз в рамках того же logical query. Интервал можно изменить через
  `MONEY_FIRST_BRAVE_MIN_INTERVAL_SECONDS` без изменения исследовательского бюджета.
- Браузер (`cua_repl`) — для поисковиков и страниц, до которых не достаёт провайдер. `curl` для обычных
  страниц не использовать.
- `scripts/sources.py` — TED (бюджеты), Wayback (версия страницы на дату), HN Algolia (голос практиков).
  Те же флаги `--assignment` и `--role`.
- Сырые ответы складываются byte-for-byte в `runs/<run-id>/sources/`; утверждения ссылаются на
  `source_id`, а sidecar фиксирует MIME, расширение, длину и SHA исходных bytes. `/tmp` запрещён.
- Бюджет: один semantic query = один запрос даже с provider fallback; открытие страниц бюджет не тратит.
- Контакты с покупателями, покупки, кампании и публикации требуют отдельного разрешения.

## Запуск с телефона

Прогон запускается из мобильного приложения Claude как облачная сессия по этому репозиторию.

Окружение настраивается один раз на claude.ai/code: уровень сети **Custom** со списком доменов
(`api.deepseek.com`, `api.search.brave.com`, при необходимости `api.ted.europa.eu`,
`hn.algolia.com`, `archive.org`) и переменные `DEEPSEEK_API_KEY` и `BRAVE_API_KEY`.

**Поле Setup script оставьте пустым.** Setup-скрипт стартует в неопределённом рабочем каталоге, и
`pip install -r requirements.txt` там падает с `No such file or directory`, а сессия вообще не
открывается. Зависимости ставит SessionStart-хук из репозитория: `.claude/settings.json` вызывает
`scripts/install_pkgs.sh`, который получает `$CLAUDE_PROJECT_DIR` и потому всегда находит корень
проекта. Локально скрипт выходит сразу, ничего не устанавливая.

Дальше в сессии достаточно команды `/research <тема и бюджет>`: она ведёт оркестратора по всему
циклу — гипотезы, задания, воркеры, приёмка, решения, отчёт, коммит и отправка в Telegram.
Артефакты прогонов лежат в git, поэтому облачная сессия видит предыдущие прогоны из клона, а её
результаты возвращаются пушем.

Стоимость распределяется так: оркестратор только раздаёт задания и принимает результаты, а все
исследовательские ходы идут по дешёвой модели через воркеров.

## Дашборд

`docs/pipeline-map.html` — автономная страница со снапшотом всех прогонов: данные, стили и скрипт
встроены в файл, серверу и сети она не нужна.

```
python3 scripts/pipeline_viewer.py --open
```

Вкладки: **Обзор** (что это за проект и где мы стоим, простым языком), **Источники** (каждое
сохранённое обращение наружу: кто из агентов его сделал, зачем и попало ли оно в утверждения),
**Агенты и модели** (запрошенная и фактическая модель роли, форма генерирует команду
`scripts/routing.py set`), **Кандидаты**, **Технически** (стадии, хронология, лимиты).

Страница ничего не записывает: она показывает состояние и выдаёт команду, которую выполняет человек.
После изменения конфигурации или новых прогонов её нужно пересобрать.

## Признаки неготовности

- Нет привязанного фактического ID агента — работа не выполнена, что бы ни лежало в очереди.
- Утверждение опирается на временный путь, пересказ или сниппет вместо сырого источника.
- Неизвестное значение превращено в ноль или в «никто не платит».
- Квалификация выставлена без принятых `money`, `distribution`, `feasibility`, `skeptic`, `judge`.
- Источник скачан, но ни одно утверждение на него не ссылается: бюджет потрачен без следа в выводах.
- Агент не передал `--assignment`: на дашборде источник виден как «не атрибутирован» и объяснить,
  зачем его тянули, уже нельзя.
